# Your first repository

Start with one repository and a small, verifiable issue. Fugue gives each
repository its own tracker project, board, credentials and persistent agent team.
You can add more repositories later without reconfiguring the first.

## Install and open Fugue

For a local source installation, install Git, GitHub CLI, Node.js and Rust using
rustup. The checkout's `rust-toolchain.toml` selects the required Rust version.
Install the native `rkat` CLI if you want to create or select model accounts
through setup. A [release bundle](../scripts/distribution/README.md) includes it
alongside all five Fugue executables.

```sh
git clone https://github.com/lukacf/meerkat-fugue.git
cd meerkat-fugue
cargo install --locked --path .
meerkat-fugue serve --port 8788
```

Open [Fugue on this machine](http://127.0.0.1:8788/). For a hosted installation,
use its authenticated HTTPS address instead. The service user's machine needs
the repository's build tools and network access to GitHub/GHE, the tracker and
the model provider. A credential alone does not establish that network access.

Keep the service user's home directory and Fugue state on durable storage.
Use `--state-dir /absolute/private/path` to choose another private state location.
Fugue refuses to store managed credentials inside a Git checkout.

## 1. Connect the repository

Choose **Repositories > Add repository** and paste its HTTPS GitHub or GitHub
Enterprise address, such as `https://github.com/example/service`.
Fugue derives the host, owner and repository. Each added repository opens its own
configuration screen.

Choose how the service accesses GitHub:

- **GitHub CLI** uses `gh` authentication on the machine running Fugue. For GHE,
  authenticate that exact hostname with `gh auth login --hostname git.example.com`.
- **Token** stores the token privately for this repository connection.

Save the connection, then **Check account access**. The authenticated account must
be able to clone the repository and, for delivery, push a branch and open a PR.
An existing checkout is an advanced option; its origin must match the selected
repository. Fugue normally clones it for you.

## 2. Choose the issue tracker

Use built-in tickets to try Fugue without a tracker account, or connect an
existing Linear or Jira project.

For Jira, supply the site, account email and API token, then select the project
key and issue type. Load its available statuses and map intake, active, review,
merge and terminal work to the project's existing workflow. Fugue validates
transitions; it does not alter a shared Jira workflow. A selective JQL filter
isolates Fugue issues inside a larger project and is required in browser setup.
For a filter such as `labels = "fugue-app"`, enter `fugue-app` in **Labels for new
issues**. The Board applies these labels when creating Jira tickets, so they
appear in this repository's queue. Separate multiple labels with commas.

For Linear, supply the API key and project/team selection. Ensure the selected
account can read and update issues, comments and the configured workflow states.
See [Jira and GitHub Enterprise](./jira-and-github-enterprise.mdx) or the
[configuration reference](./configuration.mdx) for exact fields.

Keep **Allow merge when GitHub reports no CI checks** off unless you have made
that decision for this repository. Missing checks are distinct from successful
checks. Pending or failing checks still block a merge when the exception is on.

## 3. Select model access

AI authentication belongs to Meerkat. Select an existing rkat account, connect
an API key, or use credentials already provided to the service environment.
The default model follows the Meerkat recommendation used by this Fugue release.

Connecting an API key sends it to native rkat authentication through stdin;
Fugue stores the resulting binding reference. This updates rkat's default API-key
account for that provider. Review the selected account before saving.

Browser OAuth support depends on the provider and native rkat. For Copilot or
remote-host sign-in, complete `rkat auth login` in a terminal on the execution
host, then refresh the account list. Your Fugue browser login grants operator
access; it is separate from the model account used by agents.

## 4. Prepare and start

Save all three connections, check the workspace, then start Fugue. Preparation
checks access and creates the checkout. Repository mapping then designs and
reviews the specialist team and has its members study their domains. This uses
model tokens and can take several minutes.

Watch preparation under **Repositories**. A ready team includes specialists for
this repository, not only generic planner/coder/reviewer roles. Execution agents
join the same native mob as those specialists. If preparation fails, read its
reported cause, repair the connection or configuration and use the retry action.

## 5. Run a small issue

Open the repository's **Board** and create an issue with:

1. A concrete result, such as adding a missing regression test and its fix.
2. Acceptance criteria that can be checked locally.
3. The relevant test command and any external resources the team may use.

Put it in the configured intake lane. Follow its workpad and inspect the real
agent conversations under **Agents**. Specialists keep domain knowledge and
receive notifications when subscribed paths on the remote default branch change.

Review the diff, test evidence and independent review before requesting the
final PR gate. Use the configured merge action only when the gates are satisfied.
Fugue rechecks the PR and policy at merge time. Verify the resulting merged PR
and terminal issue state; a finished agent message alone is not delivery proof.
