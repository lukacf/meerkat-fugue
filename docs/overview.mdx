# How Fugue works

Fugue turns issues into reviewed code changes. It connects GitHub or GitHub
Enterprise repositories to built-in tickets, Linear or Jira, and runs persistent
Meerkat agent teams on a host you control.

A repository is the unit of work. It owns its tracker/project, queue, checkout,
credentials and native mob. Multiple repositories share one operator application
and one native agent console.

## Setup creates the team

During preparation, Fugue maps the repository and proposes specialists based on
its actual domains. An independent formation review checks the team, then the
specialists study their code and retain their knowledge in native agent memory.
They register file and folder subscriptions. Fugue polls the remote default
branch and notifies the relevant specialists when those paths change.

Preparation is separate from daily issue work. You do not repeat repository
mapping for each ticket. Ticket leads and execution members join the existing
repository mob, with prompts naming its specialists and requiring consultation
and domain handoffs.

## Issues carry the work

An eligible issue receives an isolated workspace. The repository coordinator
and issue team plan, implement and review the work, recording durable evidence
in native runtime state and a tracker comment headed `## Fugue Workpad`.

The workpad is the human-readable record: scope, plan, test results, review and
PR links. It does not replace typed review results or native lifecycle state.
Tracker lanes project that lifecycle and expose configured operator actions.
Jira retains its existing status names and transitions.

The delivery path is:

```text
Issue intake -> Planning and implementation -> Review -> PR gate -> Merge
                         |                        |
                         +---- blockers/rework ---+
```

A merge requires the configured review and check evidence for the actual PR
head. A merge action does not deploy the application unless a deployment
procedure is explicitly configured. No reported CI checks, failed tests and a
successful check result are different outcomes.

## Three daily places

| Place | Use it for |
| --- | --- |
| Home | Issues in attention lanes, retries, active work and preparation problems. |
| Board | The repository's actual tracker lanes, issue details and operator actions. |
| Agents | Native conversations, members, topology, Memory, Work Graph, logs and health. |

**Repositories** holds occasional setup and configuration. The repository
selector retains context between pages. The shared console exposes all teams;
its native Memory and Work Graph panels select an individual runtime.

## What you operate

Fugue runs with the service user's permissions. Repository tools, hooks and build
commands execute on that host. Use trusted repositories and credentials whose
scope matches the work. Fugue is not an OS sandbox.

Every admitted browser user is a full operator of the instance. Use separate
instances for operators who must not share repository and credential authority.
Keep remote access behind an authenticated HTTPS gateway, and preserve the
service user's home and application state across upgrades.
