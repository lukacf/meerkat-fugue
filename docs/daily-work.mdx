# Daily work

Start at **Home**. Choose a repository to narrow the work context, or keep
**All repositories** to see each team's board and preparation status together.
The navigation stays in the same order: Home, Board, Agents, then Repositories
and the browser Session menu.

## Find what needs attention

Home groups issues from configured attention lanes and issues awaiting retry.
An attention lane is a request to inspect the issue, not proof that a merge is
ready. Open the issue to read its workpad, comments and review evidence.

Work in progress comes from each repository's board and native runtime status.
Setup and access shows stopped repositories, incomplete configuration,
preparation failures and unavailable boards. A failed read is shown as an error,
not an empty queue. Refresh retries the read; previously loaded data may be stale
when the update fails.

Recently finished includes terminal tracker states. A terminal Jira status may
represent either completed or canceled work. Use the runtime outcome and merged
PR to distinguish them.

## Work from the board

All repositories shows a separate board for each repository. Choose **Open board**
to create issues, filter work or use that repository's issue editor.

Use a small, explicit acceptance contract in each issue. State the desired
behavior, relevant tests and any permitted external effects. Comments let you
answer the team's questions without rewriting the original request.

If Jira creates the issue but Fugue cannot confirm its initial status, the form
keeps the issue reference and shows **Open [issue key]**. Check that existing
issue instead of submitting another one. Its title, description and initial
lane stay locked in the creation form; edit them from the issue itself.

If an attachment upload is rejected after creation, use **Retry attachments** to
upload to the same issue. Refreshing the tab preserves the issue reference and
draft text for that repository and tracker; select the pending files again before retrying.
Changing the repository's tracker starts a separate recovery context.
Choose **Done** to close this recovery form and start a separate issue. If the
browser says it could not save recovery details, keep the tab open until finished.
If creation fails without returning an issue reference, check the tracker before
trying again: the server may have accepted a request whose response was lost.

Jira files are uploaded as native issue attachments. If Jira does not confirm
the full upload, the form asks you to check the existing issue and stops offering
a blind retry. Some files may already be present. If Jira accepts the files but
the following comment is not confirmed, Fugue keeps your comment draft and tells
you to check the issue before posting again. Do not re-upload the accepted files.

The warning and your comment draft survive a reload in the same tab, including
when you refresh while the request is still pending. A gateway error or an
incomplete success response also requires checking the issue. A confirmed
rejection permits retry; an unknown result does not.

After checking the issue in your tracker, choose **I've checked the issue** and
confirm the reconciliation. This enables a new submission without resending
anything. It removes the pending file selection and keeps your comment draft,
so remove any text already posted before submitting again. This is a manual
reconciliation step, not a guarantee that the original request ran only once.

Review and merge controls follow the configured lane actions. Read the action's
label before saving a lane change: a configured action can start a review or
merge procedure. Ordinary status changes and procedure triggers are distinct.

Before requesting merge, check:

- The PR targets the intended repository and branch.
- Test and review evidence covers the current head, not an earlier revision.
- Blockers are resolved and required review gates are complete.
- CI is successful, or this repository has an explicitly authorized no-checks
  policy. Pending and failed checks remain blockers.

After the action, confirm the PR is merged and the tracker reflects the result.
If merge fails, inspect its reason and refresh the evidence before trying again.

## Follow a review

A review coordinator may be quiet while its selected specialists are working.
Open **Agents** to inspect their conversations and the review's Work Graph
obligations. The coordinator receives native completion notifications and checks
the original review results before continuing; you do not need to send it
reminders or start another review to keep it running.

A completed specialist turn is not a merge approval. The configured merge gate
still requires all selected reviews, current PR and CI evidence, and resolution
of blocking obligations. If progress stops, retain the issue, PR head and review
references and inspect the reported blocker. Do not delete the review or close
its obligations merely to advance the board.

## Inspect the team

**Agents** is the native shared Meta console. Use its roster to select an
addressable agent and read or send messages. The repository coordinator handles
repository-wide work; an issue lead coordinates its ticket. Specialists own
repository domains and can explain their context and subscriptions.

Use **Topology** for membership and native peer links, **Logs** for events and
**Health** for runtime availability. A roster count alone does not establish
working communication between members.

**Memory** and **Work Graph** are scoped to a native runtime. Select the team
inside the panel. Switching teams clears the prior team's content while the new
read is in progress. Memory exposes native records and their details; Work Graph
exposes tasks, dependencies and evidence. Availability follows the runtime's
capabilities and access policy.

In Memory, an **UNVERIFIABLE** assessment is separate from the records list:
it means that assessment cannot establish a result, not that the team has lost
its memory. Open **Records** to inspect available records and their details.
A loading error, an access denial and an empty result are different outcomes;
keep the reported error before retrying. Do not delete runtime state to clear an
assessment warning.

## Change a connection

Open the repository, then **Repository settings**. Finish active work before
stopping its runtime and reopening setup. Saved conversations and issues remain
on disk. Save the changed connections, check the workspace and start it again.
An empty repository/tracker token field preserves the existing credential only
when the host and account still match.

Browser access, tracker/repository access and model access are separate:

| Symptom | Check |
| --- | --- |
| Sign-in page or rejected browser request | Renew the browser session at the host gateway. |
| Board cannot read or update issues | Tracker credentials, project scope and transitions. |
| Clone, fetch or PR operation fails | GHE/GitHub network reachability and repository credentials. |
| Agent cannot contact its model | Native rkat account, binding and provider reachability. |
| Live console stops updating | Service health and streaming connectivity; reconnect before assuming work stopped. |

Signing out clears the browser's gateway session. Teams keep running. Changing
an AI account affects agent access; it does not change who may sign in to Fugue.

For service restarts, backup restoration or failed upgrades, use the
[operations guide](./operations.mdx). Preserve the failed run's evidence before
retrying or cleaning up its workspace.
