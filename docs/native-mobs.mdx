# Native execution and tracker projection

Native execution is Fugue's normal runtime for `fugue.yaml`. In a managed
repository, issue leads and execution members join the persistent repository
mob alongside its initialized domain specialists. The shared console shows
those real members. An issue run is not a second isolated team or another
console. Explicit workflow installations use their configured native runtime.

Fugue observes structural native events and reconciles evidence from Meta, the
workspace, the selected tracker and GitHub/GitHub Enterprise. Jira, built-in
Fugue tickets and Linear share this lifecycle boundary.

## Tracker projection model

Tracker lanes project native execution into the repository's configured
workflow. Fugue retains observations, detects external changes and informs the
repository coordinator. Issue leads coordinate their issue's work; the host
applies scoped tool permissions and validates terminal handoff evidence.

The default planner/coder/reviewer workflow uses coarse operator lanes:

| Lane | Meaning |
| --- | --- |
| `Queue` | Intake queue for eligible issues. |
| `Active` | Execution is active; phase details belong in labels, Workpad, WorkGraph and Meta. |
| `Review` | Requests the configured independent review procedure. |
| `Deploy` | Requests guarded merge and, when configured, deployment. |
| `Done` | The requested work and required handoff are verified complete. |

`tracker.lanes.ready` (historically `linear.lanes.ready`) selects intake.
`linear_projections.*.node_lanes` maps native activity to tracker status. These
historical key names work with all supported trackers. `Backlog`, `Queue`,
`Active`, `Review`, `Deploy`, `Blocked`, `Done` and `Canceled` are defaults,
not required Jira status names. Map Jira's existing statuses during setup.
See [Jira workflow mapping](./jira-and-github-enterprise.mdx#scope-and-workflow).

## Template selection

Fugue chooses a template from `selection.by_label` or
`selection.default_template`:

```yaml
selection:
  default_template: planner_coder_reviewer
  by_label:
    docs: planner_coder_reviewer
    risky-change: planner_coder_reviewer

mob_templates:
  planner_coder_reviewer:
    linear_projection: planner_coder_reviewer
    max_review_cycles: 3
    members: [planner, coder, reviewer]
```

```yaml
linear_projections:
  planner_coder_reviewer:
    node_lanes:
      planner: Active
      coder: Active
      reviewer: Active
    node_phase_labels:
      planner: fugue:phase:planning
      coder: fugue:phase:implementing
      reviewer: fugue:phase:reviewing
    aggregate:
      precedence: [Active]
      fallback: Active
    terminal_lanes:
      succeeded: Done
      failed: Active
      cancelled: Canceled
```

Issue execution is prompt-driven: the issue lead coordinates its worker
members through native communication and consults the repository specialists.
Labels route work to the configured template and review-cycle limits. Optional
`flow` selects a supported role/review contract. Members still coordinate
in-process through Meta; Fugue does not launch a second `rkat-rpc` process or
call a separate `mob/flow_run` endpoint.

## Required member tools

Planner, coder, and reviewer profiles normally need:

- `mob` for Meerkat mob and flow tools.
- `mcp:jira` for Jira issue/Workpad tools, or `mcp:linear` for Linear and the
  built-in tracker's compatible host tools.
- `mcp:github` for the GitHub/GHE tools allowed by the member's authority.
- `shell` and `git` for code-changing members.

Fugue supplies issue and repository scope to the configured tools. Members can
inspect the issue and PR and update Workpad evidence without repeating those
identifiers on every call. Jira's companion binary is `fugue-jira-mcp`; Linear
uses `fugue-linear-mcp`. Built-in tickets use host-provided tools without a
Linear server or token. Historical `linear_*` names, including
`linear_move_issue`, route to the selected tracker and remain subject to role,
repository and terminal-state checks.

Issue leads and the repository coordinator have broader lifecycle and handoff
authority than ordinary execution members. Merge always goes through the
configured Fugue host action, which checks native review, current PR/CI and Work
Graph evidence. The standalone `fugue-github-mcp` server does not offer merge;
`FUGUE_GITHUB_ALLOW_MERGE` does not enable a standalone bypass.

The MCP boundary must expose protocol-compatible `tools/list` descriptors with
`inputSchema`, not provider-style `input_schema`.

## Native review completion

Review admission binds the coordinator's actual native member and session to the
selected review runs. Caller identity comes from the native dispatch context,
not from model-supplied arguments. When that context includes retained work,
Fugue forwards it unchanged; the native runtime enforces whether governed work
is required. Ordinary native sessions can admit review without it. Retrying the
same request and key recovers the original run references rather than creating
replacement reviews.

After its initial status read, a coordinator with pending reviews ends its turn.
The native runtime queues completion notifications, allowing the coordinator to
resume without polling or a monitoring helper. A notification reports terminal
status; it does not carry an approval verdict. The coordinator re-reads all
original references and invokes the configured completion action only after
every selected review is terminal. Failed or canceled reviews remain blockers.

The host verifies native results, reviewer independence and the current PR head.
The configured final merge gate also checks required CI and Work Graph
obligations before merging. Recovery must preserve the original requests and both native mob and runtime stores.
Restore them together with the matching executable release when rolling back;
replacing only the binary does not undo changes to stored observer or
continuation data.

## Workpad handoff contract

Workers maintain exactly one persistent tracker comment headed
`## Fugue Workpad`. For issue-scoped production smokes, an issue-specific
heading such as `## LUC-123 Workpad` is preferred so operators can prove there is
exactly one Workpad for that issue and no duplicate generic Fugue Workpad. It
should contain Markdown task lists for:

- Plan
- Acceptance criteria
- Progress
- Validation
- Pull request or Handoff

Good Workpad updates are concrete. Avoid opaque evidence such as `text:"ok"`.
Record commands, test names, PR URLs, branch-scoped CI evidence or check
conclusions, and reviewer findings. Branch-scoped CI evidence means checking the
current issue branch or PR head rather than relying on a stale SHA-only check
result from an earlier handoff attempt. Keep Meta mechanism telemetry out of the Workpad:
tool catalogs, readiness gate details, flow ids, and launch diagnostics belong
in trace logs or recent events unless they are part of a human-facing blocker.
Fugue may use a minimal pending-planner placeholder, but the
planner/coder/reviewer/repo agent own the actual checkbox content.

Post-merge Meta retake smokes should also prove the upstream Meta console
path. For an autonomous kickoff smoke, create the issue while the browser
console is already open and verify Fugue picks it up from `Queue` without manual
intervention. The pre-existing console session must show the real repo
`fugue/kapellmeister` member plus active issue planner, coder, and reviewer
members with real session ids without relying on a manual browser refresh. The
planner, coder, and reviewer rows must show active peering wired to
`fugue/kapellmeister`, not a mock, stale, issue-mob container, or issue-local
replacement Kapellmeister entry. During execution, Playwright must observe live
transcript/event updates from Meta for each member.

Tracker lanes remain a Fugue/Kapellmeister projection of native facts.
Ordinary execution members report lifecycle facts to the issue lead or
repository coordinator. Only members with the configured lifecycle authority
may project tracker lanes, and PR handoff requires a green reviewer gate.

After a Fugue service restart, reopen the Meta console from the same
pre-existing Playwright browser context and verify Meta, not Fugue, replays
each member's transcript/tool history for the session ids observed before
restart. The restart smoke is green only when durable session snapshots re-admit
those member sessions: the console must not show `runtime_restore=failed`, and
service logs must not mention `missing durable session snapshot` for those ids.
Treat missing member transcript/tool history or stale active rows after the mob
reaches its terminal lane as smoke failures to investigate rather than accepted
completion evidence.

During restart recovery, an issue-specific heading such as `## LUC-123 Workpad`
is also canonical. If both the generic and issue-specific headings are present,
keep the most evidence-rich comment: issue-specific checkbox
plan, role checkoffs, exact validation commands, PR URL, CI/check conclusions,
merge SHA, and completion handoff. Placeholder progress from a restarted host
must not overwrite PR, check, or merge evidence that agents already recorded.

## Projected Lane Ownership

Lane movement is owned by the issue lead for the issue. Planner, coder, and
reviewer members write Workpad, validation, review, and handoff evidence and
report lifecycle facts to the issue lead. Kapellmeister keeps the repo-wide
view and starts or resumes issue execution in the repository mob. Fugue host
tools enforce the configured authority and record internal lane changes in the
same observation journal used by polling.

For the default planner/coder/reviewer profile, the issue lead projects active
planner, coder, and reviewer work to `Active`; the detailed role/phase is
recorded as labels, WorkGraph/Workpad evidence, and Meta runtime state.
Accepted completion projects to the configured success status. If the tracker
drifts from the recorded lane, Fugue reports the external observation to
Kapellmeister and the issue team.

## Review loops

In `planner-coder-reviewer`, red review, CI failures, or PR feedback are
recorded for focused replanning while the tracker remains on the configured active
lane. Legacy or noncanonical intake/rework signals are repaired or reported into
`Queue`/`Active` semantics instead of becoming steady lifecycle projections.
`Human Review`, `Merging`, and `In Review` are not special Fugue lifecycle
states; merge and PR monitoring belong to the repo-level handoff policy or
explicit mob nodes.

Keep review cycles bounded with `max_review_cycles` so a bad loop escalates
instead of running forever.

## Recovery evidence

Native status rows include recovery facts such as:

- Meta run id and recent structural events.
- Workspace path, branch, head SHA, and dirty flag.
- Tracker Workpad run evidence and PR mentions.
- GitHub PR URL, state, and head SHA when available.
- `review_required` if facts are missing or contradictory.

A restarted Fugue process uses durable evidence to recover active work instead
of trusting stale in-memory state.

Treat a restart-time terminal Meta `Cancelled` event as a recovery signal, not
as an automatic tracker cancellation decision. Fugue should reconcile cancellation
with Workpad, workspace, branch, PR, checks, and merge facts before choosing
retry, focused rework, handoff completion, or an operator-confirmed canceled
lane. Post-recovery smoke tests should use a fresh issue and should leave
Workpad evidence for the PR, check, merge, and final handoff that made the
outcome safe.
