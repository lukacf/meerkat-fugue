# Development guide

This guide covers local validation, coding rules, documentation changes, and the
ignored real E2E suite.

## Safe validation

Run before opening a PR:

```bash
cargo fmt --check
cargo check --all-targets --locked
cargo test --all-targets --locked
cargo clippy --all-targets --locked -- -D warnings
cargo run --locked -- --help
```

These checks do not create live Linear, GitHub, or Meta resources.

## Real E2E suite

`tests/real_e2e.rs` is ignored by default because it creates live Linear and
GitHub resources and runs real Meerkat sessions. Do not run it casually.

Run it only in an operator-approved disposable environment:

```bash
set -a
source ~/.zshrc
set +a

MEERKAT_FUGUE_REAL_E2E=1 \
MEERKAT_FUGUE_E2E_POLICY_MODE=native_only \
MEERKAT_FUGUE_E2E_KEEP_RESOURCES=1 \
cargo test --test real_e2e -- --ignored --nocapture
```

Useful controls include:

- `MEERKAT_FUGUE_E2E_LINEAR_TEAM_KEY`
- `MEERKAT_FUGUE_E2E_GITHUB_OWNER`
- `MEERKAT_FUGUE_E2E_ISSUE_COUNT`
- `MEERKAT_FUGUE_E2E_POLICY_MODE`
- `MEERKAT_FUGUE_E2E_MERGING_STATE`
- `MEERKAT_FUGUE_E2E_IN_REVIEW_STATE`
- `MEERKAT_FUGUE_E2E_CREATE_MISSING_LINEAR_STATES`
- `MEERKAT_FUGUE_E2E_KEEP_RESOURCES`

## Code style

Follow `AGENTS.md`:

- prefer typed structs and enums over carrying `serde_json::Value` through the
  system;
- return `Result` instead of swallowing mechanism errors;
- avoid `unwrap()` and `expect()` in library code;
- prefer allocation-conscious iterators and display helpers;
- use `slab` for stable keys that survive collection mutation;
- keep domain models separate from billing and usage metadata;
- use `IndexMap` when iteration order matters.

## Documentation changes

Documentation should be operator-actionable:

- state whether commands are safe or destructive;
- name required credentials and external resources;
- include rollback or handoff guidance for live operations;
- keep examples aligned with `fugue.example.yaml`, backend onboarding docs, and CLI help;
- preserve the native Meta execution model.

When changing config fields, update:

- `fugue.example.yaml`;
- `docs/configuration.mdx` and `docs/configuration.md` if the Markdown contract
  is still referenced by tests;
- backend/onboarding docs when generated queue shape changes;
- relevant operator/development docs;
- tests that assert parsing/default behavior.

## Branch and PR hygiene

Keep changes focused on the Linear issue. For documentation-only work, prefer a
single commit that updates MDX docs, README links, and any doc reference tests.
Run the safe validation set before requesting review.
